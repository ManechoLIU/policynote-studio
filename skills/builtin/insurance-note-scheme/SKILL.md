# 保险图文方案工作台

> 需求单 → 多套可比方案 → 分项溯源 → 选稿改稿 → 人工确认导出。
> **一套方案 = 封面图＋封面文案＋标题＋正文＋溯源**，不是选题建议、大纲或一句方向。
> 本技能只管流程、结构、溯源与版本；第 3–5 步的选题、标题、封面文案、正文与改稿判断一律执行 [insurance-xhs](../insurance-xhs/SKILL.md)。
> 交付标准：每套都有能打开的封面图、能直接复制的标题正文、能点开的案例链接、能核对的事实状态。

## 先判断走哪条路

| 用户诉求 | 走哪里 |
|---|---|
| 说“出方案/给方案/先出方案/给我几个方向”，但没说数量 | 先反问一句“要 4 套比较，还是 1 篇成稿？”，不自行假设 |
| 要 4/5/6 套、多版封面、并排比较 | 本技能·多套模式 |
| 在“出方案”后选了 1 篇，或明确“就写一篇但要留需求单和改稿记录” | 本技能·单篇模式 |
| 一上来只说“帮我写一篇/改一篇”，没有方案语境 | 直接 `insurance-xhs` |
| 只改标题、只改开头、只审一篇 | `insurance-xhs` 对应单点流程 |
| 要发布、要投流、要数据复盘 | 发布/归因技能，本技能不代发 |

只反问一次：用户答“4 套/几套/多版”就进多套模式，答“1 篇/就这个”就进单篇模式；答完不再重复确认。

### 两种模式

| | 多套（默认） | 单篇 |
|---|---|---|
| 第 3 步 / 目录 | 4 套（可 5–6）/ `方案A`–`方案D` | 1 套 / `方案A` |
| 门禁 | `check` | `check --single` |

单篇不是“简化版”：可以少做三套，但不能少需求单、溯源、改稿快照和导出。

## 发布隔离（硬边界）

第 1–5 步一律不进入发布流程：不读、不调发布或草稿技能；不运行 `skills/shared/scripts/xhs_publish.py` 的任何子命令（含 check、whoami）；不询问是否保存草稿。系统提示“仅保存平台草稿”只约束真正发布，不是现在进入草稿流程的理由。第 5 步 `export` 即止，发布等用户另一条明确指令。

## 开工前读这些（按需，不整包加载）

- **必读**：[insurance-xhs](../insurance-xhs/SKILL.md)，写整篇再读 `../insurance-xhs/references/writing-workflow.md`、`../insurance-xhs/references/title-writing.md`、`../insurance-xhs/references/xhs-copy-craft.md`。
- **重疾险**：`../insurance-xhs/references/critical-illness-craft.md`；有情绪与观点要求时加 `../insurance-xhs/references/emotion-and-opinion.md`。
- **案例层索引**：`../insurance-xhs/references/critical-illness-data-index.md`，只看索引按 ID 取；本技能不需要日历、账号数据和联网搜索，事实核不到就标待核。
- **事实与风控**：`../insurance-xhs/references/evidence-and-value.md`、`../insurance-xhs/references/compliance.md`、`../insurance-xhs/references/content-risk-rules.md`。
- **封面视觉**：模板已锁定配色、字号与四种构图，直接填 `cover.json`；不再选风格、不读其他视觉风格。

## 五步流程

卡住时再查 `references/flow.md`（步骤细则）与 `references/provenance.md`（溯源写法），不必通读。

### 第 1 步 需求单（不查案例库）

产出 `需求单.md`（模板见 `assets/templates/需求单.md`）。字段：主题、必须包含的信息、目标人群、使用场景、语气、产品事实、表述边界、缺口与假设。

- 从用户原话里拆字段，不要求用户填表；缺的字段先写“假设”，第 2 步只在无法假设且影响结论时问。
- 需求单是内部底稿：不检索案例、不定标题，写完直接继续，不停下等确认。

### 第 2 步 补齐信息（只问真正阻塞的）

| 缺什么 | 怎么处理 |
|---|---|
| 产品名、条款版本、保额/保费口径、能否点名 | 没说就按“通用重疾险、不点名、不写具体数字”继续；只有用户提到具体产品却缺版本时问一次 |
| 读者所处状态（已投保/待投保/理赔中/给孩子配） | 从原话判断；判断不了按“正在考虑投保”继续，并写明假设 |
| 人群、场景、语气、字数、配图风格 | 按画像与常识假设，写明“本稿假设：…”继续 |

- 模式已定的那一轮不再提问；第一轮最多问模式 1 个问题，并附带默认说明，不要求用户逐条回答。
- 问过没答的，按默认继续，不重复问同一问题；用户说“你定”就直接采用假设。
- 只有“用户点名了具体产品、却没有条款版本”这类会写错事实的缺口才值得停一次，其余不阻塞。

### 第 3 步 生成方案（多套默认 4，单篇 1）

多套必须真的不同：读者入口不同、文章骨架不同、读完的下一步不同。只换标题或换配图不算一套。

| 套 | 读者入口 | 常见骨架 |
|---|---|---|
| A | 具体困惑：我这种情况要不要买/够不够 | 攻略清单、答疑 |
| B | 反常识判断：大家都这么说，真的吗 | 反常识观点 |
| C | 算账与条件：钱花在哪、哪笔不必花 | 避坑揭秘、拆报价 |
| D | 过程与避坑：经纪人实际怎么判断 | 服务实录、避坑揭秘 |

可按主题替换入口，但多套不能挤在同一入口。动笔前先在 `方案对比.md` 写清每套“这套与另外三套的区别”，写不出就换角度；这一步是内部检查，不向用户二次确认。单篇模式只保留一套，但仍要写清它相对其他三种常见写法的取舍。

每套四件：封面图（`cover` 的 a/b/c/d 四种布局）、封面文案（≤12 字，一句判断，不能两个问句并列）、标题（≤20 字）、正文（300–700 字，四套合计 ≤3000）。四套一次写进一个 `content.json`（结构见 `references/content-schema.md`），跑 `scripts/scheme.py build` 落盘、渲染封面并过门禁；不要逐文件手写，也不要用 apply_patch 改中文路径。

**封面只走模板**：只允许 `cover.json` 的 a/b/c/d 四种 layout + `scheme.py cover`（PIL，无需浏览器）。禁止自写 PIL/HTML、禁止用 Playwright 或其他卡片技能替代；需要新构图先问用户。

其余硬约束：不加大渐变、不用 emoji 当图标、不伪造保单/理赔截图；不写“最/第一/保证/稳赚/100%/人人适合”；数字必须与事实台账一致，没依据的数字不上封面。

生成后先跑 `scripts/scheme.py check`（单篇加 `--single`）；没 PASS 不发交付消息，继续修。PASS 只代表结构齐全，事实仍要人工核对。

### 第 4 步 分项溯源（每套都做，不只做选中的）

每套写 `溯源.md`，两张表：

- **参考溯源**：标题、封面、正文各一行，写参考案例（ID＋链接）、借鉴点、不复用什么。
- **事实清单**：每条主张写类型、依据来源、版本或口径、状态（已核/待核/不适用）、失效时间。

规则：

- 链接只能来自案例层索引，不得编造；没有合适案例就写“无直接对标：按方法层《…》生成”，并写清差异。
- 借鉴点写“为什么有效”，不写“参考了这篇”；原帖的身份、经历、评论不能变成经纪人自己的。
- 事实三档：已核＝能指出来源与版本；待核＝正文同步标 `【待核实】`，且不得作结论或封面大字；不适用＝删除该主张。
- 相似度：不得整段搬运，连续 20 字以上雷同就改写；结构可学，句子不抄。

### 第 5 步 选稿与改稿

- 用户选定一套后，只改他点名的部分；没点名的地方不动，不趁机重写全文。
- 改稿走 `scripts/scheme.py revise`：先快照原稿，再写入新稿，追加修改意见；不原地覆盖。
- 每次改完复核三件事：标题是否仍由正文兑现、事实是否仍成立、封面文案是否同步。
- 改到第 3 版仍不满意，回第 3 步换角度，不继续在错角度上打磨。
- 导出用 `scripts/scheme.py export`，单文件含标题、封面、正文、溯源、修订记录；导出件标“待人工确认”。
- 导出即止：不接发布器、不跑草稿预检、不问“要不要保存草稿”。发布等用户另一条明确指令。
- 不代替机构审核；用户之后真要发布时，再提醒“先报备，再发表笔记（明亚APP-我的-自助服务-发文报备）”。

## 三层知识怎么用（不混为一谈）

| 层 | 现在在哪 | 用在哪一步 | 能否写回 |
|---|---|---|---|
| 案例层 | `../insurance-xhs/assets/research/critical-illness-20261122/`：原帖链接、作者、采集时间、互动、本地原图、正文、核对状态 | 第 3 步检索、第 4 步引用 | 只读；新案例先进候选，人工核对后才入库 |
| 方法层 | `../insurance-xhs/references/`：标题模式、封面构图、正文结构、叙事角度与适用场景 | 第 1–5 步全程 | 可沉淀“方法候选”，人工筛选后回写，不自动写 |
| 事实层 | 项目内 `事实台账.md`＋产品条款与官方材料 | 第 2 步定边界、第 3 步约束、第 4 步核对、第 5 步复核 | 可更新，但必须带来源、版本、失效时间 |

运行顺序不属于知识库：需求解析 → 检索与生成 → 来源绑定 → 事实/相似度检查 → 局部修改与版本管理。经纪人反馈先落到 `assets/方法候选.md`，不直接改知识库。

案例层口径：34 篇已核正文、其中 26 篇有本地原图，50 篇目标未完成；不把 34 说成 50，不把高互动当专业结论正确。

## 产物结构

```
outputs/<主题>/
├── 需求单.md
├── 事实台账.md
├── 方案对比.md          # 多套并排；单篇写取舍说明
├── 方案A/ 方案B/ 方案C/ 方案D/   # 单篇模式只有 方案A
│   ├── 封面.png
│   ├── 方案.md          # ## 标题 / ## 封面文案 / ## 正文
│   └── 溯源.md
├── 修订记录.md
├── 导出/
│   └── <主题>-方案A-v2.md
└── assets/
    ├── covers/cover.json
    ├── snapshots/       # 改稿前的原稿
    └── 方法候选.md
```

## 命令

```bash
# 多套模式：建骨架（需求单、事实台账、修订记录、四个方案目录）
python skills/builtin/insurance-note-scheme/scripts/scheme.py init --topic 重疾险-等待期怎么讲

# 单篇模式：只建方案A
python skills/builtin/insurance-note-scheme/scripts/scheme.py init --topic 重疾险-等待期怎么讲 --variants A

# 一次写完四套：content.json（含 brief）→ 需求单/方案/溯源/对比/台账/封面 + check（推荐）
python skills/builtin/insurance-note-scheme/scripts/scheme.py build --topic 重疾险-等待期怎么讲 --input D:/tmp/content.json

# 封面：填 assets/covers/cover.json 后一次渲染四套（PIL，无需浏览器）
python skills/builtin/insurance-note-scheme/scripts/scheme.py cover --topic 重疾险-等待期怎么讲

# 交付前硬门禁：多套不足 4 套直接 FAIL；封面尺寸、标题/正文字数、溯源三行与事实状态
python skills/builtin/insurance-note-scheme/scripts/scheme.py check --topic 重疾险-等待期怎么讲

# 单篇模式的门禁（不提示“少于 4 套”）
python skills/builtin/insurance-note-scheme/scripts/scheme.py check --topic 重疾险-等待期怎么讲 --single

# 交付文案：四套标题表 + 每套封面/正文/溯源链接，原样发出
python skills/builtin/insurance-note-scheme/scripts/scheme.py deliver --topic 重疾险-等待期怎么讲

# 改稿：先快照，再写入新稿，追加修订记录
python skills/builtin/insurance-note-scheme/scripts/scheme.py revise --topic 重疾险-等待期怎么讲 --variant A --note "开头太慢，换成客户原话" --from D:/tmp/A-方案.md

# 导出选中方案（标题/封面/正文/溯源/修订记录）
python skills/builtin/insurance-note-scheme/scripts/scheme.py export --topic 重疾险-等待期怎么讲 --variant A

# 交付后登记到内容库（可选，让工作台显示封面与成品）
python skills/shared/scripts/manifest.py meta --topic 重疾险-等待期怎么讲 --title "重疾险等待期：4 套方案" --platform 小红书 --kind xhs-note --status draft --cover 方案A/封面.png --deliverables 方案A/方案.md,方案B/方案.md,方案C/方案.md,方案D/方案.md
```

## 交互节奏（一次做完，不逐步停）

- 用户没说模式：只问一句“4 套比较，还是 1 篇成稿？”，同时说明默认（无产品按通用重疾险、不点名；读者按当前处境），答完即做。
- 模式已定：不再提问，一次做完需求单→方案→溯源→门禁再交付；中途只在开始渲染封面时给一句进度，不要求回复。
- 开工顺序固定：读 SKILL、案例索引、content-schema → init → 写 content.json → build → 交付；不插播日历、画像深读或联网搜索。
- 不出现“回复继续/下一步/我会在下一步/这轮先暂停”；补文件、渲染、自检不需要用户许可；本轮没做完就说明剩余项并继续做。
- 开工一句话说清要做什么并立刻执行，不播报内部动作；交付文案用 `scheme.py deliver` 生成并原样发出，四套封面/正文/溯源一个不漏。
- 问过没答的按默认继续，不重复问；不弹“卡片风格选哪种”。
- 同名项目已存在且不是本轮创建：换 `<主题>-2` 继续，不覆盖、不询问；本轮创建的直接补齐。
- 封面必须真实渲染成功；全程不出现“保存草稿/发布”。

## Profile 与边界

- 有画像：身份、服务人群、语气、红线读 `profiles/<名>/`，与当次要求冲突时以当次要求为准。
- 无画像：不编身份、从业年限、客户数、理赔结果；需要身份时留占位并说明。
- 不做：代发笔记、代替核保或理赔结论、承诺流量与转化、自动写回知识库。
- 封面与正文里的每个数字都要能回到事实台账；回不去就删掉或标待核实。
